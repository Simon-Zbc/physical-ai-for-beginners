# はじめに

[第9章](./09_強化学習.md)では、強化学習で Reach タスクを学習しました。報酬だけを手がかりに、ロボットが自分で動き方を見つけられることを確かめた一方で、2つの難しさも見えました。

- **報酬を書くのが難しい**：抜け穴のある報酬を書くと、エージェントはそれを確実に見つけて悪用した
- **試行錯誤の回数が多い**：Reach だけで 300 万ステップ（シミュレーション時間で約 17 時間分）の試行が必要だった

そこで本章では、発想を変えます。**報酬を書く代わりに、人間がやって見せた「お手本」（示範、デモンストレーション）をまねて学ぶ** のです。これが **模倣学習（Imitation Learning、IL）** です。

模倣学習は、いまの物体操作のロボット学習の中心にある手法です。ただし、「お手本をそのまままねる」だけでは、意外なところでつまずきます。本章では、そのつまずきを1つずつ見ていきます。

本章のゴールは次の4つです。

- 模倣学習の基本形 **Behavior Cloning（BC）** が「示範を教師データにした教師あり学習」であることを理解し、強化学習との違い（必要なもの・コスト）を整理する
- BC の2つの落とし穴、**誤差の雪だるま** と **「平均」を学んでしまう問題（多峰性）** を、身近な例で理解する
- それを乗り越える **ACT**（アクションチャンク + Temporal Ensembling）と **Diffusion Policy**（拡散モデルで行動を生成）の考え方を、数式に頼らずに理解する
- 障害物を左右どちらからでも避けられる2関節アームで、3つの方策を **PyTorch で手書き** し、同じ示範から学習させて違いを数値で確かめる

:::note info
**前提と実行環境**
- 本章のコードは **CPU だけで動きます**（GPU は不要）。筆者の環境では、1つの方策の学習が約1分で終わります
- 必要なのは **PyTorch**（CPU 版で十分）と NumPy・Pillow だけです。第9章で使った Stable-Baselines3 と Gymnasium は使いません。インストール方法は 5.1 節を参照してください
- 第9章の2関節アームの環境を土台にします。第4章（逆運動学）と第5章（PD 制御とアクションチャンク）の内容が何度か出てきます
:::

# 1. 模倣学習とは

## 1.1 お手本をまねる：教師あり学習としての模倣

新しくチームに入ったエンジニアが、ベテランの運用作業を覚える場面を想像してください。手順書がなくても、ベテランの操作ログ（「この画面が出たら、このボタンを押した」）を大量に見れば、だいたい同じように操作できるようになります。

模倣学習の最も素朴な形、**Behavior Cloning（BC、行動クローニング）** は、まさにこれです。

1. お手本役（人間や、よくできた制御器）にロボットを動かしてもらい、**「そのときの状態」と「そのときお手本がした行動」の組** を記録する
2. 状態を入力、行動を正解ラベルとして、ニューラルネットワークを **普通の教師あり学習** で学習する（損失は、出力と正解の二乗誤差 = MSE）

画像分類で「画像 → ラベル」を学ぶのと同じように、「状態 → 行動」を学ぶだけです。新しいアルゴリズムは何もいりません。

この考え方は古く、1989年には CMU の **ALVINN** が、カメラとレーザー距離計の入力からハンドルの向きを出力するニューラルネットワークで、道路に沿って車を走らせる研究を発表しています[^alvinn]。1991年の論文では、**人間の運転を見て、5分足らずでハンドル操作を学習できた** と報告されています[^alvinn-1991]。35年以上前から、「人のまねをして運転を覚える」ことは試みられていたのです。

## 1.2 強化学習との違い

第9章の強化学習と並べると、違いがはっきりします。

| | 強化学習（第9章） | 模倣学習（本章） |
|---|---|---|
| 人間が用意するもの | **報酬**（何がよいかの採点ルール） | **示範**（どう動けばよいかのお手本） |
| 学び方 | 試行錯誤で、報酬が増える行動を探す | 示範の行動を、教師あり学習でまねる |
| 必要な試行 | 大量（第9章の Reach で 300 万ステップ） | 学習中にロボットを動かす必要はない |
| 性能の上限 | 報酬が正しければ、人間を超えることもある | **基本的に示範の質が上限** |
| 主な落とし穴 | 報酬の抜け穴（報酬ハッキング） | 示範にない状況、示範のばらつき（2 節） |

「洗濯物をたたむ」ような物体操作では、「うまくたためた」を報酬として書くこと自体が難しい、という話を第9章 5.4 節でしました。模倣学習なら、**たたみ方を説明する代わりに、たたんで見せればよい** のです。

## 1.3 示範はタダではない

ただし、模倣学習にもコストがあります。強化学習のコストが「計算機の時間」だとすれば、模倣学習のコストは **「人間の時間」** です。

実際のロボットの示範は、人間が **遠隔操作（テレオペレーション）** で集めるのが一般的です。たとえば ACT の論文では、人間が手元の小さな操作用アーム（リーダー）を動かし、それに追従する作業用アーム（フォロワー）の動きを記録して、基本的に1タスクあたり 50 本の示範を集めています[^act]。数十本でも、人が実機の前に座って、1本ずつ丁寧に操作する必要があります。大規模なデータセットになると、何十人もの人が何か月もかけて集めています（6 節）。

また、**示範の質が、そのまま方策の質の上限になります**。お手本がぎこちなければ、まねた方策もぎこちなくなります。

本章の実践では、人間の代わりに **脚本示範者（手書きの経路計画プログラム）** に示範をさせます。いくらでも、何度でも同じ示範を作れるので、実験の条件をそろえやすいからです。本物の示範は人間の遠隔操作から来ること、脚本示範者はその代役であることを覚えておいてください。

# 2. BC の2つの落とし穴

BC は、教師あり学習としては何も間違っていません。それでも、ロボットを動かすと失敗することがあります。原因は大きく2つです。

## 2.1 落とし穴①：誤差が雪だるま式に増える

画像分類では、1枚の画像を少し間違えても、次の画像には影響しません。ところが、ロボットの方策は **自分の行動が、次の入力（状態）を決めます**。

```mermaid
flowchart LR
    A["方策が少しずれた<br/>行動を出す"] --> B["示範にない状態に<br/>少しだけ入る"]
    B --> C["見たことのない状態なので<br/>さらにずれた行動を出す"]
    C --> D["もっと示範から<br/>離れた状態へ"]
    D --> C
```

示範には「正しい道を進んでいる状態」しか入っていません。方策が少しでも道をはずれると、そこは **示範で一度も見たことのない状態** です。そこで出す行動は当てにならず、さらに道をはずれ……と、誤差が雪だるま式に大きくなっていきます。これを **誤差の累積（compounding error）**、または **分布シフト（covariate shift）** と呼びます。

カーナビに例えると、「正しいルート上での曲がり方」だけを覚えた運転手は、一度道を間違えると、そこからの戻り方を知らない、という状況です。

## 2.2 対策：DAgger と DART

この問題への古典的な対策が、2011年に Ross らが提案した **DAgger（Dataset Aggregation）** です[^dagger]。

1. 示範で BC を学習する
2. 学習した方策で、実際にロボットを動かしてみる（当然、少し道をはずれる）
3. **方策が自分で行ってしまった状態について、お手本役に「ここでは本当はどうすべきか」を答えてもらい**、データに追加する
4. 追加したデータで学習し直す。これを繰り返す

「道を間違えた地点からの戻り方」を、あとから教えてもらうわけです。効果は大きいのですが、**お手本役がいつでも答えてくれる** 必要があります。人間に何度も付き合ってもらうのは大変です。

もう少し手軽な方法が、2017年の **DART** です[^dart]。示範を集めるときに、**お手本の行動にわざとノイズを加えて実行** します。すると、ロボットは正しい道から少しずれた状態に入り、そこでのお手本の「正しい行動」も記録できます。最初から「少しずれた状態からの戻り方」をデータに含めておく、という考え方です。本章の実践のデータ収集でも、この考え方を取り入れています（5.3 節）。

なお、本章の実践では、誤差の累積そのもの（示範からのずれが時間とともにどう広がるか）は数値では測っていません。ここでの説明は理屈と先行研究によるもので、DAgger は演習3で試せるようにしています。

## 2.3 落とし穴②：「平均」を学んでしまう

2つ目の落とし穴は、本章の主役です。

ロボットの手先の前に障害物が1つあり、その向こうに目標があるとします。お手本役の人は、あるときは **左** から、あるときは **右** から障害物を避けました。どちらも正解です。

```text
          目標
           ●
     ╭─────────────╮
  左の道   (障害物)   右の道
     ╰─────────────╯
           ○
          起点
```

このデータで BC を学習すると、何が起きるでしょうか。BC の損失は、正解との **二乗誤差（MSE）** でした。同じ状態に対して「左（−12 cm）」と「右（+12 cm）」の2種類の正解があるとき、二乗誤差が最も小さくなる出力は、2つの **平均** です。

$$
\frac{(-12) + (+12)}{2} = 0 \text{ cm}
$$

0 cm、つまり **障害物の真ん中** です。左の答えと右の答えをそれぞれ見れば正しいのに、平均すると、どちらのお手本もしなかった、最悪の答えになってしまいます。

このように、1つの状況に正解が複数ある性質を **多峰性（multimodality）** と呼びます（正解の分布に「山」が複数あるという意味です。1つ1つの山、ここでは「左の道」と「右の道」を **モード** と呼びます）。MSE で学習する BC は、**状況ごとに1つの答えしか出せない** ので、「左 **または** 右」という答えを表現できません。

[第4章](./04_逆運動学.md)の IK を思い出してください。2関節アームには、同じ手先位置に対して「肘を上げる解」と「肘を下げる解」の2つの解がありました（第4章の例では、肘の角度が +86.2° と −86.2°）。この2つの関節角を平均すると、肘の角度は 0°、つまり **腕を伸ばしきった姿勢** になり、手先はどちらの解とも違う場所へ行ってしまいます。**正解が2つある問題で、答えを平均してはいけない** という点で、まったく同じ構図です。

ただし、これは理屈の上での話です。実際にロボットを閉ループで動かすと、方策の出力が次の状態を変えるので、もう少し複雑なことが起きます。5.5 節では、筆者の実験で「平均化」が実際にどう現れたか（そして、予想どおりには現れなかったこと）を、正直に報告します。

# 3. ACT：未来の行動をまとめて出す

2023年に Zhao らが発表した **ACT（Action Chunking with Transformers）** は、安価なロボットアームの組 **ALOHA** で、電池のスロットへの差し込みのような細かい両腕作業を、約 10 分ぶんの示範から学習し、80〜90% の成功率を報告しました[^act]。ACT の工夫のうち、本章では次の3つを扱います。

## 3.1 アクションチャンク：1回で k ステップ先まで

普通の BC は、毎ステップ「次の1ステップの行動」を出します。ACT は、**未来の k ステップぶんの行動の列（アクションチャンク）** をまとめて出力します。

| | BC | アクションチャンク |
|---|---|---|
| 1回の推論で出すもの | 次の1ステップの目標関節角 | 未来 k ステップぶんの目標関節角の列 |
| 決定の回数 | 毎ステップ | k 分の1 に減らせる（Temporal Ensembling を使うときは推論は毎ステップ。実行する行動は、重なったチャンクの合意になる） |

ACT の論文は、チャンクの利点を2つ挙げています[^act]。

- **決定の回数が減る**：k ステップ分をまとめて決めるので、タスクの実質的な長さ（決定の回数）が k 分の1 になり、2.1 節の誤差が積み重なる機会が減る。ただし、3.2 節の Temporal Ensembling を使う場合は推論を毎ステップ行い、実行する行動は、重なった複数のチャンクの「合意」（重み付き平均）になる
- **「今の状態だけ」では決められない動きを表現できる**：論文は、**示範の途中の「一時停止」** のように、1ステップずつの方策では表現しにくい動きを例に挙げています

2つ目の点を考えてみます。お手本役の人が、作業の途中で手を止めて少し考え、また動き出したとします。止まっている間、状態は変わりません。すると、**まったく同じ状態に対して「止まる」というラベルが何回も付き、最後の1回だけ「動き出す」というラベルが付きます**。1ステップずつまねる BC は、その状態では「止まる」と覚えるのが自然です。チャンクなら、「止まった先で、どう動き出すか」まで、ひとつながりの列として覚えられます。5.6 節で、これを実験で確かめます（結果は、「Temporal Ensembling と組み合わせたときに効く」という、少し意外なものになりました）。

なお、ACT の行動は **関節トルクではなく、目標関節角** です。[第5章](./05_制御と軌道生成.md) 6.1 節で見たように、方策は目標位置を出し、それを低レベルの PD 制御が追従します。ACT の論文は、遠隔操作の記録で、フォロワーではなく **リーダーの関節角を行動のラベルに使う** ことが重要だと述べています[^act]。本章の実践も、同じく目標関節角を行動にしています。

## 3.2 Temporal Ensembling：第5章の宿題

チャンクを k ステップに1回だけ出して、その間は前に出した列をそのまま実行すると、チャンクの切れ目で動きがカクッと変わることがあります。

ACT は、**チャンクを毎ステップ出し直し**、同じ時刻に向けた複数のチャンクの予測を **重み付きで平均** して実行します。これが **Temporal Ensembling** です[^act]。

| チャンクを出した時刻 | 時刻 t に向けた予測 | 時刻 t+1 に向けた予測 | 時刻 t+2 に向けた予測 | … |
|---|---|---|---|---|
| t−2 | ■ | ■ | ■ | … |
| t−1 | ■ | ■ | ■ | … |
| t | ■ | ■ | ■ | … |

時刻 t に実際に実行するのは、「時刻 t に向けた予測」の列に縦に並んだ予測の、重み付き平均です。

重みは指数関数 $w_i = \exp(-m \cdot i)$ です。$i$ は、同じ時刻に向けた予測を古い順に並べた番号で、最も古い予測が $i = 0$ です。つまり ACT では、古い予測ほど重みが大きくなります（$m$ は小さな定数）[^act]。[第5章](./05_制御と軌道生成.md) 6.2 節で、方策の出力周期と制御周期の差を埋める3つ目の方法として「アクションチャンク + 平滑化」を紹介し、実践は本章に回していました。ここで、その宿題を回収します。

## 3.3 CVAE：示範者の「気分」を吸収する（概念だけ）

ACT にはもう1つ、**CVAE（条件付き変分オートエンコーダ）** という仕組みが入っています。人間の示範には、同じ状況でも「今回は少し速く」「今回は少し回り道して」といったばらつきがあります。ACT は、このばらつきを **「スタイル」を表す変数 $z$** に吸収させるように学習します[^act]。

ただし、論文では、**実行時には $z$ を平均値（0）に固定** して、チャンクを決定的に出力しています[^act]。つまり、実行時の ACT は「状況ごとに1つの答え」を出します。本章の最小実装では CVAE を省略しました（5.8 節）。

# 4. Diffusion Policy：平均ではなく「分布」を学ぶ

2.3 節の「平均」の問題に、正面から答えるのが、2023年に Chi らが発表した **Diffusion Policy** です[^dp]。

## 4.1 画像生成 AI と同じ仕組みで、行動を「描く」

Stable Diffusion のような画像生成 AI を使ったことがあるかもしれません。名前のとおり、これは **拡散モデル（diffusion model）** という仕組みで動いています。以下では、拡散モデルの代表的な定式化である **DDPM**[^ddpm] に沿って、考え方だけを説明します。

- **学習**：きれいな画像に、いろいろな強さのノイズを混ぜる。ネットワークには **「この画像に、どんなノイズが乗っているか」** を当てさせる
- **生成**：完全なノイズ（砂嵐）から出発し、ネットワークが推定したノイズを **少しずつ取り除く** ことを何十〜何百回も繰り返す。すると、もっともらしい画像が浮かび上がってくる

Diffusion Policy は、これを **画像の代わりにアクションチャンク** でやります。「ノイズまみれの行動の列」から、観測（今の状態）を手がかりにノイズを少しずつ取り除き、もっともらしい行動の列を削り出します。

式で書くと、学習で使うのは次の2つの式だけです。正解のチャンクを $x_0$、ノイズを $\epsilon$、ノイズの強さの段階を $t$ とすると、

$$
x_t = \sqrt{\bar\alpha_t}\, x_0 + \sqrt{1 - \bar\alpha_t}\, \epsilon, \qquad
\text{損失} = \left\| \epsilon - \epsilon_\theta(x_t,\ t,\ \text{観測}) \right\|^2
$$

$\bar\alpha_t$ は「元の信号がどれだけ残っているか」で、$t$ が大きいほど 0 に近づきます。ネットワーク $\epsilon_\theta$ の仕事は、**乗っているノイズを当てること** です。損失は BC と同じ二乗誤差ですが、当てる対象が「行動」ではなく「ノイズ」になっている点が違います。

## 4.2 なぜ「左か右か」を選べるのか

BC は、状態を入れると答えが1つ出てくる関数でした。Diffusion Policy は、**同じ状態からでも、出発点のノイズが違えば、違う答えが出てきます**。

直感的には、こう考えられます。学習したネットワークは、「ノイズまみれの行動列を、示範にありそうな行動列の方へ押し戻す方向」を知っています。示範には「左の道」と「右の道」の2つの山があり、その間（真ん中の道）には示範がありません。出発点のノイズが少し左寄りなら左の山へ、右寄りなら右の山へと押し戻されていき、**示範にない真ん中には落ち着きません**。

つまり、BC が「答えの平均」を学ぶのに対し、Diffusion Policy は **「答えの分布」そのもの** を学び、そこからサンプルを1つ取り出して実行します。論文も、多峰的な行動の分布を自然に表現できることを主な利点に挙げています[^dp]。

## 4.3 代償：遅い

その代わり、Diffusion Policy は **遅い** のが弱点です。BC はネットワークを1回呼べば行動が出ますが、Diffusion Policy は、ノイズを取り除く処理のたびにネットワークを呼ぶので、1回の行動の生成に、10〜100 回程度の呼び出しが必要です。

論文では、学習を 100 段階、生成を **DDIM** という方法で 10 段階に間引き、GPU（Nvidia 3080）で 0.1 秒の推論時間を実現しています[^dp]。それでも、BC に比べれば重い処理です。[第5章](./05_制御と軌道生成.md)で見た「方策の周期と制御の周期の差」の問題は、ここでも効いてきます。実践では、この遅さも測ります（5.7 節）。

## 4.4 Temporal Ensembling を使わない理由

Diffusion Policy は、ACT の Temporal Ensembling を使いません。代わりに、**生成したチャンクのうち先頭の数ステップだけを実行し、そこで新しいチャンクを生成し直す**（receding horizon 制御）という方法をとります。論文の標準設定は、16 ステップを予測して 8 ステップを実行する、というものです[^dp][^dp-code]。

なぜ平均しないのでしょうか。Diffusion Policy の出力は、毎回ランダムにサンプルされます。あるときのサンプルが「左の道」、次のサンプルが「右の道」だったとすると、**その2つを平均した行動は、また障害物の真ん中を指してしまいます**。せっかく分布を学んで平均化を避けたのに、実行のときに平均化を持ち込んでしまうわけです。そこで、1つのサンプルを一定時間「信じて」実行します。論文も、1回の実行（ロールアウト）の中では1つのモードにコミットする、と述べています[^dp-site]。

        for _ in range(DECIMATION):
            active = ~collided                                # 衝突した環境はその場で止める

## 5.3 示範者と示範データ（`expert.py`・`collect_demos.py`）

脚本示範者は、起点 → 経由点 → 目標を、なめらかな曲線でつなぎます。経由点は、障害物の中心から左か右へ 12 cm（`DETOUR = 0.12`）の位置です。障害物の半径 5 cm と手先の半径 2 cm に、余裕を持たせた値です。

```python:expert.py（抜粋）
def plan(start_xy, target_xy, side, pause_steps=0):
    """起点 -> 経由点 -> 目標 の目標関節角列 (EPISODE_STEPS, 2) を作る

    経路は経由点をちょうど通る2次ベジェ曲線（経由点で速度が連続）で、時間配分は min-jerk。
    pause_steps > 0 のときは、経由点でいったん止まって pause_steps ステップ待ち、そのあと動き出す。
    """
    via = OBS_CENTER + np.array([side * DETOUR, 0.0])
    ctrl = 2 * via - (start_xy + target_xy) / 2          # u = 0.5 で経由点を通る制御点
    t = np.arange(EPISODE_STEPS)
    if pause_steps == 0:
        u = _min_jerk(np.clip(t / (DEMO_STEPS - 1), 0, 1))
    else:                                                # 前半（起点→経由点）、停止、後半（経由点→目標）
        half = DEMO_STEPS // 2
        first = 0.5 * _min_jerk(np.clip(t / (half - 1), 0, 1))
        second = 0.5 + 0.5 * _min_jerk(np.clip((t - half - pause_steps) / (half - 1), 0, 1))
        u = np.where(t < half + pause_steps, first, second)
    u = u[:, None]
    xy = (1 - u)**2 * start_xy + 2 * u * (1 - u) * ctrl + u**2 * target_xy
    return ik(xy)
```

曲線（2次ベジェ曲線）の上の点を、時間配分を第5章の5次多項式（min-jerk）にして並べ、各点を第4章の解析的 IK で目標関節角に変換しています。IK の解は、肘の向きを1つ（`q2 > 0`）に固定しました。2.3 節で見たように、肘の解が途中で入れ替わると、示範そのものに「2つの答え」が混ざってしまうからです。

`collect_demos.py` は、この示範者を並列に走らせて記録します。

## 5.4 3つの方策（`policies.py`・`train.py`）

3つの方策は、どれも **隠れ層 256 ユニット × 3 層の小さな全結合ネットワーク（MLP）** で、入力は第9章と同じ 10 次元の観測（関節角の cos・sin、関節速度、目標位置、目標までのずれ）です。違うのは **何を出力し、どう学習し、どう実行するか** だけです。「1つずつ考え方を足していく」ように作りました。

| | BC | チャンク（ACT の考え方） | Diffusion（Diffusion Policy の考え方） |
|---|---|---|---|
| 出力 | 次の1ステップの目標関節角 | 未来 16 ステップの目標関節角 | 未来 16 ステップを、ノイズから生成 |
| 学習の損失 | 行動の MSE | チャンクの MSE | 乗せたノイズの MSE |
| 実行 | 毎ステップ出力をそのまま実行 | 毎ステップ予測し、Temporal Ensembling で平均 | 8 ステップ実行するごとに、新しくサンプル |

### BC とチャンク：出力の形が違うだけ

```python:policies.py（抜粋）
class BCNet(nn.Module):
    """観測 → 次の行動 (B, 2)"""

    def __init__(self):
        super().__init__()
        self.mlp = mlp(OBS_DIM, ACT_DIM)

    def forward(self, obs):
        return self.mlp(obs)


class ChunkNet(nn.Module):
    """観測 → 未来 CHUNK ステップの行動 (B, CHUNK, 2)"""

    def __init__(self):
        super().__init__()
        self.mlp = mlp(OBS_DIM, CHUNK * ACT_DIM)

    def forward(self, obs):
        return self.mlp(obs).view(-1, CHUNK, ACT_DIM)

```

チャンクの学習ラベルは、「各ステップから見た、同じ示範の未来 16 ステップぶんの行動」です。示範の終わりを越える部分は、**次の示範の行動が混ざらないように**、その示範の最後の行動で埋めます。

```python:policies.py（抜粋）
def make_chunk_labels(actions, episode_index, k):
    """各ステップのラベル = 同じエピソード内の未来 k ステップの行動 (M, k, 2)

    エピソードの終わりを越える部分は、そのエピソードの最後の行動で埋める
    （次の示範の行動が混ざらないように）。各エピソードの行は時間順に並んでいる前提。
    """
    labels = np.empty((len(actions), k, actions.shape[1]), dtype=actions.dtype)
    for e in np.unique(episode_index):
        ids = np.nonzero(episode_index == e)[0]
        a = actions[ids]
        padded = np.concatenate([a, np.repeat(a[-1:], k - 1, axis=0)])   # 最後の行動を k-1 回足す
        labels[ids] = padded[np.arange(len(a))[:, None] + np.arange(k)]  # i 行目 = padded[i : i+k]
    return labels
```

### Temporal Ensembling の実装

```python:policies.py（抜粋）
class ChunkRunner:
    """毎ステップ チャンクを予測し、同じ時刻に向けた過去の予測と加重平均して実行する

    num[i, j] / den[i, j] は env i の「j ステップ後」に向けた予測の重みつき和と重みの和。
    ステップごとに1つ前へずらすので、num[:, 0] / den[:, 0] が今のステップの行動になる。
    """

    def __init__(self, net, obs_norm, act_norm, ensemble=True):
        self.net, self.obs_norm, self.act_norm, self.ensemble = net, obs_norm, act_norm, ensemble
        self.num = None                                         # 最初の呼び出しで env の数に合わせて作る

    def __call__(self, obs):
        if self.num is None:
            self.num = np.zeros((len(obs), CHUNK, ACT_DIM)); self.den = np.zeros((len(obs), CHUNK))
            self.step = np.zeros(len(obs), dtype=int)           # リセットから数えたステップ数 s
        chunk = self.act_norm.denorm(_predict(self.net, self.obs_norm, obs))   # (N, CHUNK, 2)
        if not self.ensemble:
            return chunk[:, 0]
        # 早い時刻の予測ほど重い（ACT と同じ）。w の絶対値は s とともに小さくなるが、
        # num / den の比で打ち消し合うので、効くのは予測どうしの相対的な重みだけ
        w = np.exp(-TE_M * self.step)
        self.num += w[:, None, None] * chunk
        self.den += w[:, None]
        action = self.num[:, 0] / self.den[:, 0, None]
        self.num = np.roll(self.num, -1, axis=1); self.num[:, -1] = 0   # 1ステップ進める
        self.den = np.roll(self.den, -1, axis=1); self.den[:, -1] = 0
        self.step += 1
        return action

    def reset(self, ids):
        if self.num is not None:                                # 終わった env のぶんだけ捨てる
            self.num[ids] = 0; self.den[ids] = 0; self.step[ids] = 0
```

`num[i, j]` と `den[i, j]` に、環境 i の「j ステップ後」に向けた予測の重み付きの和と、重みの和をためておきます。毎ステップ1つ前へずらすので、`num[:, 0] / den[:, 0]` が「今のステップに向けた、過去 16 回ぶんの予測の重み付き平均」になります。係数 `TE_M = 0.01` は ACT と同じ値です[^lerobot-act]。

`reset(ids)` で、**エピソードが終わった環境のぶんだけ** バッファを捨てているのも大事な点です。並列環境では、終わった環境だけがその場でリセットされるので（第7章）、全環境のバッファを捨てると、ほかの環境の予測まで消えてしまいます。

### Diffusion：ノイズを当てるネットワーク

Diffusion のネットワークは、「観測」「ノイズの乗ったチャンク」「ノイズの段階 t」を受け取り、乗っているノイズを推定します。

```python:policies.py（抜粋）
class DiffusionNet(nn.Module):
    """(観測, ノイズの乗ったチャンク, ステップ t) → 乗っているノイズの推定 (B, CHUNK, 2)"""

    def __init__(self):
        super().__init__()
        self.mlp = mlp(OBS_DIM + CHUNK * ACT_DIM + 32, CHUNK * ACT_DIM)

    def forward(self, obs, noisy_chunk, t):
        x = torch.cat([obs, noisy_chunk.flatten(1), time_embedding(t)], dim=1)
        return self.mlp(x).view(-1, CHUNK, ACT_DIM)


def predict_x0(x, eps, t):
    """x_t とノイズの推定 ε̂ から「ノイズを全部取り除いたチャンク」x̂0 を推定し、±CLIP_X0 で切る"""
    ab = ALPHA_BARS[t]
    return ((x - torch.sqrt(1 - ab) * eps) / torch.sqrt(ab)).clamp(-CLIP_X0, CLIP_X0)
```

学習の損失は `train.py` の `loss_fn` です。BC とチャンクは行動の MSE、Diffusion は 4.1 節の式どおり、正解のチャンクにランダムな段階 t のノイズを乗せて、そのノイズを当てさせます。

```python:train.py（抜粋）
def loss_fn(kind, net, obs, target):
    """1バッチぶんの loss。BC とチャンクは行動の MSE、Diffusion は「乗せたノイズを当てる」MSE"""
    if kind != "diffusion":
        return torch.mean((net(obs) - target) ** 2)
    t = torch.randint(T_DIFF, (len(obs),))                 # バッチの各サンプルにランダムなステップ t
    noise = torch.randn_like(target)
    ab = ALPHA_BARS[t][:, None, None]
    noisy = torch.sqrt(ab) * target + torch.sqrt(1 - ab) * noise   # 正解チャンクに t ステップぶんのノイズを乗せる
    return torch.mean((net(obs, noisy, t) - noise) ** 2)
```

### Diffusion：ノイズからチャンクを削り出す

生成では、純粋なノイズから出発し、100 段階かけてノイズを取り除きます。各段階では、①ネットワークの推定から「ノイズを全部取り除いたチャンク」$\hat{x}_0$ を推定し、②それと今の $x_t$ を混ぜて1段階前に進め、③最後の段階以外は少しノイズを足し直します。

```python:policies.py（抜粋）
@torch.no_grad()
def sample_chunks(net, obs_n, rng_seed):
    """DDPM の逆過程: 純粋なノイズから T_DIFF ステップかけてチャンクを作る（正規化した空間で）

    同じ rng_seed なら同じ結果になる。obs_n は正規化済みの観測 (B, 10) の tensor。
    """
    g = torch.Generator().manual_seed(rng_seed)
    x = torch.randn(len(obs_n), CHUNK, ACT_DIM, generator=g)
    for t in reversed(range(T_DIFF)):
        eps = net(obs_n, x, torch.full((len(obs_n),), t))
        x0 = predict_x0(x, eps, t)                                   # ① 元のチャンクを推定（切る）
        ab, ab_prev = ALPHA_BARS[t], (ALPHA_BARS[t - 1] if t > 0 else torch.tensor(1.0))
        # ② x̂0 と今の x_t を混ぜて、1ステップ前 x_{t-1} の平均にする（DDPM の事後分布の平均）
        x = (torch.sqrt(ab_prev) * BETAS[t] / (1 - ab)) * x0 + (torch.sqrt(ALPHAS[t]) * (1 - ab_prev) / (1 - ab)) * x
        if t > 0:                                                    # ③ 最後のステップ以外はノイズを足す
            var = BETAS[t] * (1 - ab_prev) / (1 - ab)                # 事後分布の分散 β̃_t
            x = x + torch.sqrt(var) * torch.randn(x.shape, generator=g)
    return x
```

実行器は、環境ごとに行動のキューを持ち、キューが空になった環境だけ新しいチャンクをサンプルして、先頭の 8 ステップ（`N_ACTION`）を入れます。4.4 節のとおり、Temporal Ensembling はしません。

```python:policies.py（抜粋）
class DiffusionRunner:
    """env ごとに行動のキューを持ち、空になった env だけチャンクをサンプルして先頭 N_ACTION 個を入れる"""

    def __init__(self, net, obs_norm, act_norm, seed=0):
        self.net, self.obs_norm, self.act_norm = net, obs_norm, act_norm
        self.rng = np.random.default_rng(seed)                  # サンプルごとの乱数シードを決める
        self.queue = None

    def __call__(self, obs):
        if self.queue is None:
            self.queue = np.zeros((len(obs), N_ACTION, ACT_DIM), dtype=np.float32)
            self.left = np.zeros(len(obs), dtype=int)           # キューに残っている行動の数
        empty = np.nonzero(self.left == 0)[0]
        if len(empty):
            obs_n = torch.as_tensor(self.obs_norm.norm(obs[empty]), dtype=torch.float32)
            chunk = sample_chunks(self.net, obs_n, int(self.rng.integers(2**31))).numpy()
            self.queue[empty] = self.act_norm.denorm(chunk[:, :N_ACTION])
            self.left[empty] = N_ACTION
        action = self.queue[np.arange(len(obs)), N_ACTION - self.left]
        self.left -= 1
        return action

    def reset(self, ids):
        if self.queue is not None:
            self.left[ids] = 0                                  # 次の呼び出しで、この env だけ新しくサンプルする
```

### ① E1 の BC の衝突率は 0.0%。そのかわり、片側だけを選んだ

2.3 節の理屈どおりなら、BC は左右の平均をとって障害物に突っ込むはずでした。ところが、**筆者の環境では、左右が混ざった示範（E1）で学習した BC の衝突率は、3シードとも 0.0% でした**。予想した「平均して真ん中に突っ込む」現象は、この実験では起きませんでした。

代わりに起きたのは、**シードごとに、ほぼ片側だけを選ぶ** ことでした。障害物を通った左／右の件数は、シード 0 が 2343 / 52、シード 1 が 6 / 7984、シード 2 が 6119 / 24 です。示範の半分は反対側を通っていたのに、BC はそれをほとんど再現しません。そして、どちらの側になるかは、学習のシード次第でした。

なぜ真ん中に突っ込まないのかについて、筆者は次のように考えています（推測です）。示範の左右は 50/50 でも、ネットワークの初期値やデータのわずかな偏りで、起点付近の出力はどちらかに少しだけ傾きます。手先が少しでも片側へ動くと、そこは「その側の示範」に近い状態なので、方策はますますその側の示範をまねるようになります。閉ループでは、**小さな非対称が、片側への決定的な選択に増幅される** のです。

これは「ぶつからなかったから成功」ではありません。示範者が持っていた **「左でも右でもよい」という多様性が、BC では失われた** ということです。示範者の 50/50 は、BC の中では「1つの答え」に潰れてしまいました。

一方、**Diffusion は3シードとも左右の両方を使いました**（E1 の左の割合は、シードによって 33.7〜81.7%）。成功率も 99.9〜100.0% です。

:::note warn
`experiments.py` が最後に出力する「3シードの平均」で、E1 の BC の「左」は 57.0% になります。しかし、これは「左にほぼ全部行くシード」と「右にほぼ全部行くシード」を平均した数字で、1つの BC が左右をバランスよく使ったわけではありません。片側に偏った方策を、シードをまたいで平均すると、見かけ上バランスがとれて見えるので注意してください。
:::

### ② 同じ場所から走らせると、違いがはっきりする

E1 では、シード 0 と 2 で、チャンクも左右の両方を使っています（シード 0 で 2427 / 3702、シード 2 で 2637 / 2983）。これは、Diffusion と同じように「左右を選べている」のでしょうか。

E1 でチャンクが左右に分かれたのは、起点・目標の位置が ±2 cm の範囲で毎回違ったからです。筆者が別に書いた診断スクリプト（リポジトリには含めていません）で、シード 0 のチャンクの方策を、起点だけを 1 cm 刻みの 5 × 5 の格子に置いて1回ずつ走らせると、次のようになりました（`L` / `R` = 通った側、`S` = 成功。上の行から順に起点の y のずれ −2〜+2 cm、左の列から順に x のずれ −2〜+2 cm）。

ログの見出しの「下から」は、y のずれの小さいほう（机の図で下側）から順に並べた、という意味です。表示では、いちばん上の行が y のずれ −2 cm です。

**起点が 1〜2 cm ずれるだけで、左右が決定的に入れ替わります**。チャンクは「確率的に選んでいる」のではなく、「場所によって行き先が決まっている」のです。

### ③ BC は途中で止まることがある（平均化とは別の弱点）

E1 のシード 0 では、BC の 40.5% が時間切れでした。未通過（障害物の横を通り過ぎないまま終わったエピソード）は 893 で、時間切れの件数（エピソード全体の 40.5%）より少ないので、時間切れの一部は、障害物の横を通り過ぎたあとに起きています。軌跡を描くと、起点の近くで進めなくなるものと、障害物を回ったあとで示範にない場所へずれていき、そこで止まってしまうものがあります。後者は、2.1 節の「示範にない状態に入り込み、戻れなくなる」誤差の累積と同じ見た目です（ただし、誤差の累積そのものは、本章では数値で測っていません）。E1b のシード 0 では、同じ起点から 100.0% が時間切れで、すべて未通過でした。

**Temporal Ensembling をやめると、チャンクの方策も大半が時間切れになりました**（時間切れ 87.0% / 90.8% / 100.0%）。この実験で効いていたのは、「未来 16 ステップを予測するように学習したこと」だけではなく、**過去に出した予測（動き出しを含む列）を、実行する行動に混ぜたこと** だったと考えられます。なお、チャンクを k ステップぶんそのまま実行してから予測し直す、という実行方法もあります（LeRobot の ACT は、Temporal Ensembling を使わないときの既定がこの方法です[^lerobot-act]）が、本章では試していません。

## 5.7 推論時間：Diffusion は約 20 倍遅い

推論時間（`推論[ms]` の列）は、1024 環境ぶんをまとめて1回呼び出すのにかかった時間の平均です。上に載せた `experiments.txt` は、ほかの処理で CPU が混んでいたときの実行で、時間の列が大きく出ています。CPU が空いていたときに、E2 対照を加える前のコードで行った実行（成功率や左右の件数は、すべて同じ値になりました）では、次のとおりでした。

| 方策 | 推論 [ms]（シード 0 の E1） | E1・E1b の3シードでの範囲 |
|---|---|---|
| BC | 2.686 | 2.612〜3.275 |
| チャンク | 3.100 | 2.937〜3.381 |
| Diffusion | 61.356 | 54.581〜61.659 |

**筆者の環境では、Diffusion は BC の約 20 倍の時間がかかりました**。しかも、Diffusion がサンプルを作るのは 8 ステップに1回（キューが空になった環境だけ）なので、生成1回あたりの重さは、この平均よりさらに大きくなります。100 段階のノイズ除去で、ネットワークを 100 回呼んでいるからです。論文のように DDIM で段階を間引くと速くなりますが、本章では実装を簡単にするため、間引いていません（演習4）。

`experiments.py` 全体の実行時間は、筆者の環境で、E2 対照を含めて約 12 分でした（CPU がほかの処理で混んでいたときは約 26 分）。

本章の3つの方策は、**論文の核になる考え方だけを取り出した最小版** です。「ACT」「Diffusion Policy」そのものではありません。

## 5.9 演習

1. `policies.py` の `CHUNK`（チャンクの長さ、既定は 16）を 4 や 32 に変えて `python train.py chunk` を実行し、成功率と軌跡のなめらかさがどう変わるか確かめてみましょう（`CHUNK = 1` は、Temporal Ensembling なしの BC に近くなります）。注意：`CHUNK` は Diffusion のネットワークの形も変え、`CHUNK` は `N_ACTION`（8）以上である必要があります（4 を試すときは Diffusion を使わないか、`N_ACTION` も下げます）。保存済みのチャンク・Diffusion の `.pt` は読み込めなくなるので学習し直し、試したあとは 16 に戻してください。
2. `collect_demos.py` で左右の比率を変えた示範を作り（例：左 90% / 右 10%。`rng.choice([-1, 1], episodes)` に `p=[0.9, 0.1]` を渡す）、BC・チャンク・Diffusion が、右に行く割合をどこまで再現するか比べてみましょう。
3. DAgger（2.2 節）を試してみましょう。学習済みの BC を走らせ、その途中の状態（手先の位置）から目標まで、脚本示範者で `plan` を作り直してラベルとして付け、示範に追加して再学習します。BC の「起点の近くで止まる」失敗は減るでしょうか。
4. Diffusion の拡散ステップ数 `T_DIFF`（既定は 100）を 50、20、10 に減らして学習し、成功率と推論時間（`evaluate.py` の `推論[ms]` の列）の関係を調べてみましょう。
5. （発展）第9章の PPO を、この障害物つきの環境（`env.py`）で学習してみましょう。報酬を自分で設計し、模倣学習と、成功率・動きのなめらかさ・必要な試行回数を比べます。

# 6. 産業界における模倣学習

## 6.1 強化学習とのコストの比較

本章の実践で使った示範は 200 本、合計 18946 ステップでした。第9章の PPO は 300 万ステップの試行錯誤が必要でしたから、ステップ数だけ見れば、模倣学習は 100 分の 1 以下のデータで済んでいます（ただし、タスクが違うので、成功率を直接比べることはできません）。

しかし、この比較には大きな落とし穴があります。第9章の 300 万ステップは、**シミュレータが CPU で約5分で作った** ものでした。本章の 200 本は、脚本示範者が一瞬で作りましたが、現実の示範は **人間が実機を1本ずつ操作して** 作ります。模倣学習は、試行の回数を「人間の手間」に置き換えている、と考えるのが正確です。そのため、産業界では「人間の示範を、いかに安く、たくさん集めるか」が大きなテーマになっています。

## 6.2 示範を集める道具

- **リーダー・フォロワー型の遠隔操作**：ACT の ALOHA は、人間が小型のリーダーアームを動かし、フォロワーアームがそれに追従する構成で、システム全体を 2 万ドル以内の予算で作っています。操作と記録は 50Hz です[^act]
- **ロボットなしで示範を集める**：**UMI（Universal Manipulation Interface）** は、GoPro カメラを付けた **手持ちのグリッパー** で、人間が日常の環境の中で示範を集め、それを拡散モデルの方策の学習に使います[^umi]。示範を集める場所に、ロボット本体を持ち込む必要がありません

## 6.3 大規模な示範データセット

- **Open X-Embodiment**：21 の研究機関が協力し、**22 種類のロボット** のデータを1つの形式にまとめたデータセットです。527 のスキル、160,266 のタスクを含みます[^oxe]
- **DROID**：50 人のデータ収集者が北米・アジア・欧州で 12 か月かけて集めた、**76k 本の示範（350 時間ぶん）**、564 の場面、84 のタスクからなる、「実験室の外」の物体操作のデータセットです[^droid]

## 6.4 VLA の行動出力にも、拡散の考え方

第12章で扱う VLA（Vision-Language-Action）モデルにも、本章の考え方が入っています。Physical Intelligence の **π0** は、事前学習済みの視覚言語モデル（VLM）に、**flow matching（拡散モデルの一種）で連続的な行動を出力する「action expert」** を追加した構成です[^pi0][^pi0-blog]。

- 出力は **50 ステップのアクションチャンク** で、最大 50Hz でロボットを制御する[^pi0]
- 生成は、ノイズから 10 回の積分ステップで行う（本章の Diffusion の 100 段階より少ない）[^pi0]
- 学習には、7 種類のロボット構成・68 のタスクにわたる約 10,000 時間の示範を使っている[^pi0]

後継の π\*0.6 でも、flow matching で学習した action expert が行動を出力しています[^pistar]。**アクションチャンク**（3 節）と **拡散系の生成モデル**（4 節）は、最先端の VLA でも、行動を出すための基本部品になっています。

## 6.5 模倣してから、強化学習で磨く

[第9章](./09_強化学習.md) 5.3 節で見たように、模倣学習で「だいたいできる」方策を作り、そこから強化学習で磨く、という組み合わせも増えています。

- **π\*0.6（RECAP）**：VLA を、ロボット自身の経験と人間による修正から強化学習で改善し、難しいタスクでは処理量を2倍以上にし、失敗率をおよそ半分にしたと報告しています[^pistar]
- **ConRFT**：少数の示範からの BC と Q 学習で事前に学習した後、実機で 45〜90 分の強化学習で追加学習し、8つの実タスクで平均 96.3% の成功率を報告しています[^conrft]

模倣学習で「示範の質が上限」になる問題（1.2 節）を、強化学習で超えようとする流れです。

## 6.6 LeRobot：模倣学習を手元で試す

Hugging Face の **LeRobot** は、本章で考え方だけを手書きした ACT や Diffusion Policy の本格的な実装を、データセットの形式・学習・評価の流れとまとめて提供するライブラリです。執筆時点の最新版は 0.6.1（2026年8月3日公開）で、模倣学習の方策として ACT・Diffusion などを、VLA として Pi0・Pi0.5・SmolVLA などを扱えます[^lerobot-pypi]。

# 7. まとめ

- **模倣学習（BC）** は、示範の「状態 → 行動」を教師あり学習でまねる。報酬を書かなくてよいが、示範を集める **人間の手間** がかかり、**示範の質が上限** になる
- BC の落とし穴の1つ目は **誤差の雪だるま**（示範にない状態に入ると、ずれが広がる）。対策は DAgger（ずれた状態に正解を付け足す）や DART（示範にノイズを入れる）
- 2つ目は **多峰性**。左右どちらでも正解のとき、MSE で学ぶ BC は「状況ごとに1つの答え」しか持てず、理屈の上では2つの答えの平均（障害物の真ん中）を出してしまう
- 実践では、**筆者の環境では、左右が混ざった示範（E1）で学習した BC の衝突率は3シードとも 0.0% で、真ん中に突っ込む現象は見られなかった**。代わりに、BC はシードごとに **ほぼ片側だけ** を選び、示範者の「左でも右でもよい」という多様性を失った。同じ起点から走らせると、BC とチャンクは1通りの動きしか出さず、**Diffusion だけが同じ状況から左にも右にも行けた**
- **ACT のアクションチャンク** は、決定の回数を減らし、「一時停止」のような今の状態だけでは決まらない動きを扱える。ただし Temporal Ensembling を使うときは推論は毎ステップで、実行するのは重なったチャンクの合意になる。一時停止を含む示範では、BC が経由点で止まった（時間切れ 42.2〜100.0%）のに対し、チャンク（Temporal Ensembling あり）は3シードとも 100.0% 成功した。Temporal Ensembling をやめると、チャンクの方策も 87.0〜100.0% が時間切れになったので、効いていたのは **過去の予測を実行に混ぜること** だった。**Temporal Ensembling** は、重なった予測を加重平均してなめらかにする（第5章の宿題の回収）
- **Diffusion Policy** は、画像生成と同じ「ノイズを少しずつ取り除く」仕組みで、行動の **分布** を学ぶ。代償は推論の遅さで、筆者の環境では BC の約 20 倍の時間がかかった。サンプルの平均は平均化を呼び戻すので、Temporal Ensembling の代わりに「数ステップ実行してサンプルし直す」
- 産業界では、示範の収集（遠隔操作、UMI）、大規模データセット（Open X-Embodiment、DROID）、VLA の flow matching による行動出力（π0）、模倣 + 強化学習（RECAP、ConRFT）と、模倣学習が物体操作の中心になっている

## 次回予告

**第11章「LeRobot 実践」** では、本章で考え方だけを手書きした ACT と Diffusion Policy を、Hugging Face の **LeRobot** の本格的な実装で動かします。本章の示範は、10 次元の数値を NumPy の配列に保存しただけでしたが、実際のロボット学習では、カメラ画像や複数の関節の時系列を、決まった形式のデータセットとして扱います。データセットの形式から、学習・評価の流れまで、業界で使われている道具の使い方を見ていく予定です。
